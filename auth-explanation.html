Vue d'ensemble — comment les 5 fichiers se parlent

Avant de plonger dans chaque fichier, voici la vue globale. Ces 5 fichiers forment un système cohérent où chacun a un rôle précis et unique.

┌─────────────────────────────────────────────────────────────────┐
│ DÉMARRAGE DE L'APPLICATION │
└──────────────────────────┬──────────────────────────────────────┘
│
▼
app/_layout.tsx ← premier fichier chargé par Expo Router
│ Enveloppe tout avec les Providers
│ <ThemeProvider>
│ <AuthProvider> ← lance AuthContext
│ <AuthGuard> ← surveille user + redirige
│ <TabsLayout>
│
┌──────────────────┴─────────────────────┐
│ user == null ? user != null ? │
│ ▼ ▼ │
│ app/Auth.tsx app/index.tsx │
│ (écran login) (feed home) │
└──────────────────────────────────────────┘
│
app/Auth.tsx
│ re-exporte juste AuthScreen
│
components/AuthScreen.tsx ← toute l'UI ici
│ appelle useAuth() pour obtenir login/register
│
context/AuthContext.tsx
│ login() → apiPost('/auth/login')
│ register() → apiPost('/auth/register')
│
utils/api.ts ← fetch() + JWT + gestion 401
│
BACKEND NestJS POST /api/auth/login
Règle de séparation des responsabilités
AuthScreen = seulement l'UI et la validation locale.
AuthContext = seulement la logique métier (appels API, sauvegarde token).
api.ts = seulement les requêtes HTTP.
_layout.tsx = seulement la redirection selon l'état de connexion.
Chaque fichier a une seule responsabilité.

app/Auth.tsx — le fichier de route

// app/Auth.tsx — fichier complet (3 lignes !)
import AuthScreen from "../components/AuthScreen";

export default AuthScreen;

C'est intentionnellement minimaliste. Expo Router exige qu'un fichier dans app/ existe pour que la route /Auth existe. Mais tout le vrai code est dans components/AuthScreen.tsx.

Pattern "two-file" — règle du projet
Chaque écran suit ce pattern : app/X.tsx = juste export default from components/X. Cela garde les fichiers de route propres et permet de réutiliser les composants ailleurs si besoin.

Quand Expo Router voit ce fichier, il créé automatiquement une route /Auth accessible via router.replace('/Auth'). L'URL est dérivée du nom du fichier.

components/AuthScreen.tsx — l'interface utilisateur

Structure globale du JSX

return (
  <SafeAreaView>                       ← zone sécurisée (hors encoche)
    <KeyboardAvoidingView>               ← remonte le contenu quand clavier ouvert
      <ScrollView>                        ← défilement si contenu dépasse l'écran

        <View> Logo + titre </View>
        <View> Onglets Connexion/Inscription </View>
        { error && <ErrorBox/> }           ← affichage conditionnel
        { mode === 'login'
            ? <LoginForm/>
            : <RegisterForm/> }            ← rendu conditionnel
        <View> Comptes de test </View>

      </ScrollView>
    </KeyboardAvoidingView>

SafeAreaView

Sans SafeAreaView, le contenu s'afficherait sous l'encoche (iPhone) ou la caméra punch-hole (Android). Ce composant ajoute automatiquement les marges internes nécessaires selon l'appareil.

KeyboardAvoidingView

Quand l'utilisateur appuie sur un TextInput, le clavier virtuel monte et peut cacher les champs du bas. KeyboardAvoidingView décale automatiquement son contenu vers le haut.

<KeyboardAvoidingView
  behavior={Platform.OS === 'ios' ? 'padding' : undefined}
  style={{ flex: 1 }}
>
Pourquoi Platform.OS ici ?
Sur iOS, le comportement 'padding' est nécessaire. Sur Android, React Native gère cela nativement via le manifest (windowSoftInputMode), donc undefined suffit. C'est un des rares endroits où le code doit différer selon l'OS.

ScrollView avec keyboardShouldPersistTaps

<ScrollView
  contentContainerStyle={styles.scroll}
  showsVerticalScrollIndicator={false}
  keyboardShouldPersistTaps="handled"
>

keyboardShouldPersistTaps="handled" permet de cliquer sur les boutons sans que le clavier se ferme d'abord. Sans ça, le premier tap ferme le clavier au lieu d'appuyer le bouton.

Pourquoi autant de useState séparés ?
Chaque champ a son propre état car React re-render seulement les composants dont l'état change. Si tout était dans un seul objet, chaque frappe au clavier re-rendrerait tous les champs. Les états séparés sont plus performants et plus lisibles.

Rendu conditionnel — afficher Login OU Register

// Dans le JSX — opérateur ternaire
{mode === 'login' ? (
  <View> {/* formulaire login */} </View>
) : (
  <View> {/* formulaire register */} </View>
)}

Un seul useState('login') contrôle lequel des deux blocs JSX est rendu. Quand l'utilisateur clique "S'inscrire", setMode('register') change l'état → React re-render → le formulaire registration apparaît, le formulaire login disparaît.

Styles conditionnels

// Onglet actif = fond blanc + ombre. Onglet inactif = transparent.
<TouchableOpacity
  style={[styles.modeTab, mode === 'login' && styles.modeTabActive]}
  onPress={() => switchMode('login')}
>

Le tableau de styles [styles.base, condition && styles.extra] est le pattern standard React Native pour les styles dynamiques. Si la condition est false, le deuxième style est ignoré.

Le composant InputField — un mini-composant réutilisable

InputField est un composant défini dans le même fichier qu'AuthScreen. Il encapsule un TextInput avec des fonctionnalités supplémentaires : bordure colorée au focus, et bouton "oeil" pour les mots de passe.

Code complet du composant

function InputField({ placeholder, value, onChangeText,
                       secureTextEntry = false, keyboardType = 'default',
                       autoCapitalize = 'none' }) {

  // État 1 : le champ est-il actif (en cours de saisie) ?
  const [focused, setFocused] = useState(false);

  // État 2 : le mot de passe est-il visible ?
  // Par défaut : visible si PAS un champ mot de passe
  const [visible, setVisible] = useState(!secureTextEntry);

  return (
    <View style={[styles.inputWrap, focused && styles.inputFocused]}>
      <TextInput
        value={value}
        onChangeText={onChangeText}
        placeholder={placeholder}
        placeholderTextColor="#aaa"
        secureTextEntry={secureTextEntry && !visible}   ← masquer SI mot de passe ET non visible
        keyboardType={keyboardType}                    ← clavier email ou normal
        autoCapitalize={autoCapitalize}                ← pas de majuscule auto pour email
        onFocus={() => setFocused(true)}              ← bordure violette quand actif
        onBlur={() => setFocused(false)}              ← bordure grise quand inactif
      />

      // Bouton oeil — affiché seulement pour les champs mot de passe
      {secureTextEntry && (
        <TouchableOpacity onPress={() => setVisible(!visible)}>
          <Text>{visible ? "👁" : "🙈"}</Text>
        </TouchableOpacity>
      )}
    </View>
  );
}

useState(false) — focused

  • Démarre à false (pas de focus)
  • onFocus → setFocused(true)
  • onBlur → setFocused(false)
  • Change la couleur de la bordure via style conditionnel

useState(!secureTextEntry) — visible

  • Champ email → secureTextEntry=false → visible=true
  • Champ mot de passe → secureTextEntry=true → visible=false
  • Clic sur l'oeil → toggle setVisible(!visible)

Props du composant — le "contrat d'interface"

PropTypeDéfautRôle
placeholderstring—Texte fantôme quand vide
valuestring—Valeur contrôlée (vient du parent)
onChangeTextfunction—Callback quand l'utilisateur tape
secureTextEntrybooleanfalseMasquer les caractères (mot de passe)
keyboardType"default" | "email-address""default"Type de clavier affiché
autoCapitalize"none" | "words""none"Majuscule automatique
Composant "contrôlé" (Controlled Component)
value={email} + onChangeText={setEmail} = le composant est contrôlé par React. La valeur affichée vient toujours de l'état parent (email). Chaque frappe déclenche setEmail qui met à jour l'état → React re-render → TextInput affiche la nouvelle valeur. C'est le flux à sens unique de React.

La logique des formulaires — validation et soumission

handleLogin — le gestionnaire de connexion

const handleLogin = async () => {
  setError("");                              // 1. Effacer les erreurs précédentes

  // 2. Validation locale AVANT l'appel réseau
  if (!email.trim() || !password.trim()) {
    setError("Veuillez remplir tous les champs.");
    return;                                    // ← stop, pas d'appel API
  }

  setLoading(true);                           // 3. Activer le spinner
  const result = await login(email.trim(), password); // 4. Appel au contexte
  setLoading(false);                          // 5. Désactiver le spinner

  // 6. Si échec → afficher l'erreur du serveur
  if (!result.success) setError(result.error ?? "Erreur inconnue.");
  // Si succès → AuthGuard redirige automatiquement (pas de code ici)
};
Pourquoi pas de router.push() après le login ?
Parce que login() change user dans le Context → AuthGuard dans _layout.tsx détecte le changement via useEffect([user]) → redirige automatiquement vers /. L'écran Auth n'a pas besoin de savoir où naviguer.

handleRegister — validations multiples

const handleRegister = async () => {
  setError("");

  // Validation 1 : champs obligatoires
  if (!fullName.trim() || !username.trim() || !regEmail.trim() || !regPassword.trim()) {
    setError("Veuillez remplir tous les champs."); return;
  }

  // Validation 2 : longueur du username
  if (username.trim().length < 3) {
    setError("Le nom d'utilisateur doit contenir au moins 3 caractères."); return;
  }

  // Validation 3 : longueur du mot de passe
  if (regPassword.length < 6) {
    setError("Le mot de passe doit contenir au moins 6 caractères."); return;
  }

  // Validation 4 : confirmation du mot de passe
  if (regPassword !== confirmPassword) {
    setError("Les mots de passe ne correspondent pas."); return;
  }

  setLoading(true);
  const result = await register({
    fullName: fullName.trim(),
    username: username.trim().toLowerCase(),   ← toujours en minuscule
    email: regEmail.trim().toLowerCase(),
    password: regPassword,
  });
  setLoading(false);
  if (!result.success) setError(result.error ?? "Erreur inconnue.");
};

Le bouton avec état de chargement

<TouchableOpacity
  style={[styles.submitBtn, loading && styles.submitDisabled]}  ← grisé si loading
  onPress={handleLogin}
  disabled={loading}                                             ← plus cliquable si loading
  activeOpacity={0.85}
>
  {loading
    ? <ActivityIndicator color="#fff" />        ← spinner blanc pendant l'attente
    : <Text>Se connecter</Text>                  ← texte normal sinon
  }
</TouchableOpacity>

Ce pattern est universel dans React Native : pendant un appel asynchrone, le bouton montre un spinner et est désactivé pour éviter les doubles soumissions.

context/AuthContext.tsx — l'état global d'authentification

C'est le fichier le plus important du système d'auth. Il utilise le Context API de React pour partager l'état de connexion avec toute l'application.

Pourquoi Context API ?

Le problème sans Context — "Prop drilling"
Sans Context, pour partager user entre AuthScreen, Profile, Feed, DMs… il faudrait passer user en prop à chaque composant, puis à ses enfants, puis aux enfants de ses enfants. Le Context résout ça : on met user dans un "store global" accessible par n'importe quel composant via useAuth().

Les 4 pièces du Context API

1. createContext()

  • Crée le "conteneur" global
  • Retourne un objet Context
  • Valeur initiale = null

2. Provider

  • Enveloppe les composants enfants
  • Fournit la valeur via value={...}
  • Placé dans _layout.tsx

3. useContext()

  • Lit la valeur du Context
  • Déclenche un re-render si la valeur change
  • Utilisé dans le hook custom

4. Hook custom useAuth()

  • Encapsule useContext(AuthContext)
  • Ajoute une erreur si utilisé hors Provider
  • Interface propre pour les composants

Le type AuthContextType — le "contrat"

type AuthContextType = {
  user: User | null;              // null = non connecté
  isLoading: boolean;            // true pendant la lecture d'AsyncStorage au démarrage
  login: (email, password) => Promise<{ success: boolean; error?: string }>;
  register: (data) => Promise<{ success: boolean; error?: string }>;
  logout: () => Promise<void>;
  refreshUser: () => Promise<void>;
};

useEffect au démarrage — restaurer la session

useEffect(() => {
  (async () => {
    try {
      const saved = await AsyncStorage.getItem(SESSION_KEY);  ← lire le disque
      if (saved) setUser(JSON.parse(saved) as User);          ← restaurer l'état
    } catch (_) {
    } finally {
      setLoading(false);                                       ← fin du splash screen
    }
  })();
}, []);   ← [] = s'exécute UNE SEULE FOIS au montage
Pourquoi isLoading ?
Quand l'app démarre, React monte les composants avant qu'AsyncStorage réponde. Pendant cette fraction de seconde, user est null, ce qui déclencherait une redirection vers /Auth… même si l'utilisateur était connecté. isLoading = true dit à l'AuthGuard "attends, je suis encore en train de vérifier". L'app affiche un spinner à la place.

La fonction login()

const login = async (email, password) => {
  try {
    // 1. Appel API → reçoit { token, user }
    const data = await apiPost<{ token: string; user: User }>('/auth/login', { email, password });

    // 2. Sauvegarder le JWT dans AsyncStorage
    await setToken(data.token);

    // 3. Sauvegarder les infos user dans AsyncStorage
    await AsyncStorage.setItem(SESSION_KEY, JSON.stringify(data.user));

    // 4. Mettre à jour l'état React → déclenche AuthGuard → redirection
    setUser(data.user);

    return { success: true };
  } catch (err) {
    return { success: false, error: err.message };
  }
};

La fonction logout()

const logout = async () => {
  await removeToken();                              ← supprimer JWT d'AsyncStorage
  await AsyncStorage.removeItem(SESSION_KEY);       ← supprimer les infos user
  setUser(null);                                    ← user=null → AuthGuard redirige vers /Auth
};

Le gestionnaire 401 global

useEffect(() => {
  setUnauthorizedHandler(() => {
    AsyncStorage.removeItem(SESSION_KEY);
    setUser(null);                    ← déconnecte automatiquement si token expiré
  });
}, []);

Si n'importe quel appel API retourne un 401 (token expiré), api.ts appelle ce handler → l'utilisateur est déconnecté et redirigé vers la page de login sans que chaque écran ait à gérer ce cas.

utils/api.ts — les appels réseau

Rôle général

Ce fichier centralise toute communication avec le backend. Au lieu d'écrire fetch() partout avec la même logique de token, on l'écrit une fois ici.

Gestion du JWT Token

const TOKEN_KEY = '@token';

// Sauvegarder dans AsyncStorage (après login)
export async function setToken(token: string) {
  return AsyncStorage.setItem(TOKEN_KEY, token);
}

// Lire (avant chaque requête)
export async function getToken() {
  return AsyncStorage.getItem(TOKEN_KEY);
}

// Supprimer (au logout)
export async function removeToken() {
  return AsyncStorage.removeItem(TOKEN_KEY);
}

authHeaders() — injection automatique du token

async function authHeaders() {
  const token = await getToken();
  return token ? { Authorization: `Bearer ${token}` } : {};
  // Résultat si connecté : { Authorization: "Bearer eyJhbGciOiJIUzI1Ni..." }
  // Résultat si non connecté : {}
}

apiPost() — détail complet

export async function apiPost<T>(path: string, body?: unknown): Promise<T> {
  const headers = await authHeaders();          // récupère le token

  const res = await fetch(`${API_URL}${path}`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',       // dit au serveur que c'est du JSON
      ...headers                                   // ajoute le Bearer token
    },
    body: body ? JSON.stringify(body) : undefined // sérialise l'objet en string JSON
  });

  if (res.status === 401) return handleUnauthorized(); // token expiré

  if (!res.ok) {
    const err = await res.json().catch(() => ({ message: res.statusText }));
    throw new Error(err.message);                // message d'erreur du serveur
  }

  const text = await res.text();
  return text ? JSON.parse(text) : undefined;   // désérialiser la réponse
}

Le gestionnaire 401 global

let _onUnauthorized: (() => void) | null = null;

// AuthContext enregistre ce handler au démarrage
export function setUnauthorizedHandler(handler: () => void) {
  _onUnauthorized = handler;
}

async function handleUnauthorized() {
  await AsyncStorage.removeItem(TOKEN_KEY);    // supprimer le token corrompu
  _onUnauthorized?.();                           // appeler le handler d'AuthContext
  throw new Error('Session expirée. Veuillez vous reconnecter.');
}
Flux d'une erreur 401
1. Un appel apiGet('/posts/feed') reçoit HTTP 401
2. handleUnauthorized() est appelé
3. Il supprime le token d'AsyncStorage
4. Il appelle le handler enregistré par AuthContext
5. Le handler fait setUser(null)
6. AuthGuard détecte user=null → router.replace('/Auth')
7. L'utilisateur se retrouve sur la page de login

app/_layout.tsx — le garde d'authentification

La fonction AuthGuard

function AuthGuard({ children }) {
  const { user, isLoading } = useAuth();     // lire l'état global
  const router = useRouter();                // accès à la navigation
  const segments = useSegments();            // route actuelle ex: ["Auth"] ou [""]

  // Réagit chaque fois que user, isLoading ou segments changent
  useEffect(() => {
    if (isLoading) return;                    // attendre que AsyncStorage réponde

    const onAuthScreen = segments[0] === 'Auth';

    // Non connecté ET pas sur /Auth → rediriger vers /Auth
    if (!user && !onAuthScreen) router.replace('/Auth');

    // Connecté ET sur /Auth → rediriger vers / (feed)
    else if (user && onAuthScreen) router.replace('/');

  }, [user, isLoading, segments]);

  // Pendant le chargement → afficher un spinner
  if (isLoading) {
    return (
      <View style={styles.splash}>
        <ActivityIndicator size="large" color={colors.primary} />
      </View>
    );
  }

  return <>{children}</>;   // sinon, rendre les enfants normalement
}

useSegments() — détecter la route active

Route activesegments[0]Résultat
/ (feed)"" ou "index"onAuthScreen = false
/Auth"Auth"onAuthScreen = true
/Profile"Profile"onAuthScreen = false
/conversation/123"conversation"onAuthScreen = false

router.replace() vs router.push()

router.push()

  • Ajoute l'écran à la pile de navigation
  • Bouton retour disponible
  • Utilisé pour la navigation normale

router.replace()

  • Remplace l'écran actuel (pas de retour)
  • Utilisé pour les redirections auth
  • Évite de revenir en arrière vers /Auth après login

Scénarios complets — pas-à-pas

Scénario A — L'utilisateur se connecte

1

L'utilisateur tape email + mot de passe

Chaque frappe appelle setEmail() ou setPassword(). React re-render, TextInput affiche la nouvelle valeur.

2

Il clique "Se connecter"

handleLogin() est appelé. Validation locale : champs vides ? → erreur affichée, stop.

3

setLoading(true)

Le bouton devient grisé et affiche un ActivityIndicator. L'utilisateur ne peut plus cliquer.

4

login() dans AuthContext est appelé

AuthContext appelle apiPost('/auth/login', { email, password }).

5

api.ts envoie la requête HTTP

fetch('http://backend/api/auth/login', { method: 'POST', body: JSON.stringify({email, password}) })

6

Le backend répond avec { token, user }

Le JWT est sauvegardé dans AsyncStorage. Les infos user sont sauvegardées dans AsyncStorage.

7

setUser(data.user) dans AuthContext

L'état global user passe de null à l'objet user. Tous les composants qui consomment ce contexte re-rendent.

8

AuthGuard détecte user != null

Son useEffect([user]) se déclenche. user est défini et on est sur /Auth → router.replace('/').

9

L'écran Feed s'affiche

La navigation est complète. setLoading(false) dans AuthScreen s'exécute mais ne change rien (l'écran est démonté).

Scénario B — L'app redémarre (session persistée)

1

_layout.tsx se monte — AuthProvider démarre

isLoading = true, user = null (état initial).

2

AuthGuard voit isLoading = true

Il affiche un spinner et ne redirige pas. Aucune navigation ne se produit.

3

useEffect lit AsyncStorage

Trouve les infos user sauvegardées → setUser(parsedUser). setLoading(false).

4

AuthGuard re-déclenche avec user != null

Expo Router est toujours sur / (la route par défaut). user existe et on n'est pas sur /Auth → aucune redirection, le feed s'affiche directement.

Scénario C — Erreur de login

1

Mauvais mot de passe → serveur répond 401

apiPost appelle handleUnauthorized()... Non ! Ici on n'est PAS encore connecté. Le serveur répond { message: "Identifiants incorrects" } avec un code 400 ou 401.

2

api.ts lance une Error

throw new Error(err.message) avec le message du serveur.

3

AuthContext catch l'erreur

Retourne { success: false, error: "Identifiants incorrects" }.

4

AuthScreen affiche l'erreur

setLoading(false). setError("Identifiants incorrects"). La boîte rouge apparaît sous les onglets.
