useEffect — chargement initial (une seule fois)

useEffect(() => {
  if (!user) return;

  // Requête 1 : données du profil (bio, stats, avatar)
  apiGet<UserProfile>(`/users/${user.id}/profile`)
    .then((data) => setProfile(data))
    .catch(console.error)
    .finally(() => setLoading(false));

  // Requête 2 : tous les posts/reels de l'utilisateur
  apiGet<MediaItem[]>(`/posts/user/${user.id}`)
    .then(setGridPosts)
    .catch(() => setGridPosts([]));

}, [user]);  ← re-déclenche si user change (connexion d'un autre compte)
Pourquoi deux appels API séparés ?
Profil et posts peuvent charger à des vitesses différentes. Si on les met dans un seul appel, il faudrait attendre les deux. En les séparant, le profil s'affiche dès qu'il arrive, la grille suit. Le .finally(() => setLoading(false)) sur le premier appel suffit : c'est lui le bloquant (le spinner disparaît quand le header est prêt).

useFocusEffect — rechargement à chaque retour sur l'écran

useFocusEffect(
  useCallback(() => {
    if (!user) return;

    // Recharge la grille à chaque fois qu'on revient sur cet écran
    apiGet<MediaItem[]>(`/posts/user/${user.id}`)
      .then(setGridPosts).catch(() => {});

    // Recharge les stories pour savoir si l'anneau de story est actif
    apiGet<...>("/stories")
      .then((stories) => {
        const mine = stories.find((s) => s.user.id === user.id);
        setHasStories(!!mine);
        setMyStoryImageUrl(mine?.imageUrl ?? null);
      }).catch(() => { setHasStories(false); });

  }, [user])  ← useCallback évite de recréer la fonction à chaque render
);
useEffect vs useFocusEffect — quelle différence ?
useEffect(fn, []) s'exécute une seule fois quand le composant se monte.
useFocusEffect(fn) s'exécute à chaque fois que l'écran devient actif (y compris au retour depuis EditProfile, CreatePost, etc.).

Exemple concret : si l'utilisateur crée un nouveau post depuis Profile → CreatePost → retour, la grille se rafraîchit automatiquement grâce à useFocusEffect.

Pourquoi .map() et pas FlatList ici ?

BottomMenu — Modal slide-up

Le menu "hamburger" (⋮) est un composant défini dans le même fichier que Profile. Il est rendu comme un Modal avec animationType="slide".

function BottomMenu({ visible, onClose }) {
  const { logout } = useAuth();
  const { isDark, toggleTheme, colors } = useTheme();
  const router = useRouter();

  return (
    <Modal
      visible={visible}           ← contrôlé par menuOpen dans Profile
      transparent                 ← fond semi-transparent
      animationType="slide"       ← glissement depuis le bas
      onRequestClose={onClose}    ← bouton retour Android
    >
      // Fond sombre cliquable pour fermer
      <Pressable style={styles.backdrop} onPress={onClose} />

      // Carte blanche qui monte depuis le bas
      <View style={styles.sheet}>
        <View style={styles.sheetHandle} />  ← petite barre grise décorative
        ...items du menu...
      </View>
    </Modal>
  );
}
Pattern backdrop + sheet — Comment ça marche
Le Modal transparent couvre tout l'écran mais son fond est transparent. À l'intérieur on place :
1. Un Pressable qui prend flex:1 = toute la zone sombre. Cliquer dessus → onClose().
2. Un View avec position:'absolute', bottom:0 = la carte blanche collée en bas.
Les deux se superposent via le même Modal.

Déconnexion avec confirmation — Alert.alert

const handleLogout = async () => {
  onClose();
  await new Promise((res) => setTimeout(res, 200));  ← laisser le modal se fermer d'abord

  const confirmed =
    Platform.OS === 'web'
      ? window.confirm('Êtes-vous sûr...')           ← web fallback
      : await new Promise<boolean>((resolve) => {
          Alert.alert(
            'Déconnexion',
            'Êtes-vous sûr de vouloir vous déconnecter ?',
            [
              { text: 'Annuler', style: 'cancel', onPress: () => resolve(false) },
              { text: 'Déconnecter', style: 'destructive', onPress: () => resolve(true) },
            ]
          );
        });

  if (confirmed) await logout();
};
Alert.alert() avec style "destructive"
style: 'destructive' affiche le bouton en rouge sur iOS (avertit l'utilisateur d'une action irréversible). Sur Android ça n'a pas d'effet visuel mais c'est une bonne pratique sémantique. Le pattern new Promise + resolve convertit l'Alert (callback) en une fonction async/await.

function StatBox({ value, label, onPress }) {

}

useLocalSearchParams() — comment ça marche
C'est l'équivalent de useParams() en React Router web. Expo Router sérialise les params en strings dans l'URL. Le type générique <{ fullName: string; ... }> sert uniquement à TypeScript pour l'autocomplétion — en runtime tout est toujours une string.

useEffect pour synchroniser les params

// Ré-synchronise les champs si les params changent
// (ex: reconnexion d'un autre compte sans démontage du composant)
useEffect(() => {
  setFullName(params.fullName ?? "");
  setUsername(params.username ?? "");
  setEmail(params.email ?? "");
  setBio(params.bio ?? "");
  setCurrentPassword("");
}, [params.fullName, params.username, params.email, params.bio]);

handleSave — PATCH vers l'API

const handleSave = async () => {
  // Validation locale
  if (!fullName.trim()) { Alert.alert("Validation", "Full name cannot be empty."); return; }
  if (!username.trim()) { Alert.alert("Validation", "Username cannot be empty."); return; }

  setSaving(true);
  try {
    const body = { fullName, username, email, bio };
    if (currentPassword) body.currentPassword = currentPassword;
    // currentPassword n'est envoyé que si l'utilisateur l'a rempli

    const res = await fetch(`${API_URL}/users/me`, {
      method: "PATCH", headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
      body: JSON.stringify(body),
    });

    if (!res.ok) {
      const errData = await res.json().catch(() => ({ message: "Update failed" }));
      // Le message peut être une string ou un tableau (erreurs de validation NestJS)
      const message = Array.isArray(errData.message)
        ? errData.message.join("\n")
        : errData.message;
      Alert.alert("Error", message); return;
    }

    await refreshUser();  ← met à jour le Context global avec les nouvelles infos
    Alert.alert("Success", "Profile updated.", [{ text: "OK", onPress: goBack }]);
  } finally { setSaving(false); }
};

router.replace('/EditProfile') — pas router.back()

Pourquoi replace et non back() ?
router.back() reviendrait à l'écran précédent dans la pile de navigation, qui pourrait être Profile ou EditProfile selon d'où on vient. router.replace('/EditProfile') garantit qu'on revient toujours à EditProfile, peu importe le chemin emprunté pour arriver ici.

ProfileShareSheet.tsx BOTTOM SHEET

Ce composant est le plus riche techniquement. C'est une feuille de partage animée qui combine : animation manuelle, API de partage natif, clipboard, haptics, liens profonds, et une liste de contacts filtrée.

Animation d'entrée/sortie — Animated.spring + Animated.timing

// slideAnim commence à 600 (hors écran en bas) et descend à 0 (visible)
const slideAnim = useRef(new Animated.Value(600)).current;

useEffect(() => {
  if (visible) {
    // Ouverture : spring = animation physique avec rebond
    Animated.spring(slideAnim, {
      toValue: 0,
      useNativeDriver: true,
      tension: 65,    ← rigidité du ressort (haut = plus rapide)
      friction: 11,   ← amortissement (haut = moins de rebond)
    }).start();
  } else {
    // Fermeture : timing = animation linéaire/courbe, plus contrôlée
    Animated.timing(slideAnim, {
      toValue: 600,
      duration: 220,
      useNativeDriver: true,
    }).start();
  }
}, [visible]);
// Dans le JSX — translateY appliqué à la View
<Animated.View
  style={[styles.sheet, { transform: [{ translateY: slideAnim }] }]}
>
useRef(new Animated.Value(600)).current — pourquoi useRef ?
Si on écrivait const slideAnim = new Animated.Value(600) directement dans le composant, une nouvelle instance serait créée à chaque re-render, et l'animation recommencerait depuis le début. useRef garantit que c'est la même instance qui persiste pendant toute la vie du composant.

État d'envoi par contact — sentIds (Set)

const [sentIds, setSentIds] = useState<Set<string>>(new Set());
const [sendingId, setSendingId] = useState<string | null>(null);

const handleSend = async (receiverId) => {
  if (sendingId) return;        ← anti-doublon : un seul envoi à la fois
  setSendingId(receiverId);
  try {
    await apiPost(`/users/share-profile/${username}`, { receiverId });
    setSentIds(prev => new Set([...prev, receiverId]));  ← ajouter à l'ensemble
    await Haptics.notificationAsync(Haptics.NotificationFeedbackType.Success);
  } catch {
    await Haptics.notificationAsync(Haptics.NotificationFeedbackType.Error);
  } finally { setSendingId(null); }
};
Pourquoi un Set plutôt qu'un tableau pour sentIds ?
Set garantit l'unicité et offre has(id) en O(1) (instantané peu importe la taille). Avec un tableau, on ferait includes(id) qui est O(n). Chaque ContactRow vérifie sentIds.has(item.id) à chaque render, donc la performance compte.

Alert.alert avec action destructive + mise à jour locale

const handleMinus = (person: FollowUser) => {
  Alert.alert(
    isFollowers ? "Remove follower" : "Unfollow",
    isFollowers ? `Remove @${person.username}?` : `Unfollow @${person.username}?`,
    [
      { text: "Cancel", style: "cancel" },
      {
        text: isFollowers ? "Remove" : "Unfollow",
        style: "destructive",
        onPress: async () => {
          try {
            if (isFollowers) await apiDelete(`/users/${person.id}/follower`);
            else            await apiDelete(`/users/${person.id}/follow`);

            // Mise à jour optimiste — retirer de la liste sans re-fetch
            setUsers(prev => prev.filter(u => u.id !== person.id));
          } catch {
            Alert.alert("Error", "Something went wrong.");
          }
        },
      },
    ]
  );
};
Mise à jour "optimiste" de la liste
Au lieu de re-faire un apiGet pour recharger toute la liste après la suppression, on filtre directement l'état local avec prev.filter(u => u.id !== person.id). C'est instantané, donne une sensation de rapidité, et évite un appel réseau inutile.

Ces deux écrans sont quasi-identiques. Seuls changent : le titre, l'endpoint API, l'icône vide, et le texte du message "aucun contenu".

useFocusEffect + useCallback — la combinaison standard

useFocusEffect(
  useCallback(() => {
    apiGet<GridItem[]>("/posts/saved")     ← ou "/posts/liked"
      .then(setItems)
      .catch((err) => console.warn(err))
      .finally(() => setLoading(false));
  }, [])  ← [] = la fonction ne change jamais
);
Pourquoi useCallback est obligatoire avec useFocusEffect ?
useFocusEffect compare la référence de la fonction à chaque render pour décider si elle doit re-s'abonner. Sans useCallback, une nouvelle fonction est créée à chaque render → useFocusEffect pense que le callback a changé → il se déclenche en boucle infinie. useCallback(fn, []) stabilise la référence : même fonction pour toujours.

FlatList 3 colonnes — numColumns + columnWrapperStyle

<FlatList
  data={items}
  numColumns={3}                   ← 3 items par ligne automatiquement
  columnWrapperStyle={styles.row}    ← style appliqué à chaque ligne
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => (
    <TouchableOpacity style={styles.gridItem}>
      <Image source={{ uri: item.image }} style={styles.gridImage} />
      {item.type === 'reel' && (
        <View style={styles.mediaTypeBadge}>  ← badge absolu
          <Ionicons name="play-circle" size={16} color="#fff" />
        </View>
      )}
    </TouchableOpacity>
  )}
/>
// Calcul de la taille des cellules avec Dimensions
const { width: W } = Dimensions.get('window');
const GRID_SIZE = W / 3 - 1;  ← soustrait le gap de 1.5px de chaque côté

// Dans les styles
gridItem: { width: GRID_SIZE, height: GRID_SIZE, marginBottom: 1.5 }
